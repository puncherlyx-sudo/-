## 1. P0 — критичное (подтверждено в коде main)

### 1.1 Кредиты и план меняет клиент [КОД]
- Где: `firestore.rules`, правило профиля («Action 1») разрешает клиенту менять `creditsRemaining`, `nextResetAt`; допускает `plan` in free/pro/max, `creditsRemaining` ≤ 2000 для max.
- Риск: любой пользователь через консоль браузера выдаёт себе кредиты → обход оплаты.
- Исправить: клиентские обновления `creditsRemaining`, `weeklyQuota`, `nextResetAt`, `plan`, `proUntil`, `maxMultiplier` запретить в правилах полностью; списание — только на сервере (firebase-admin, транзакция). Готовая реализация есть на ветке `ccr-dc5d7ede-r0hi61` (`server/entitlements.ts`), её нужно доработать под план `max`.
- Проверить: в консоли браузера выполнить `updateDoc(doc(db,'users',uid),{creditsRemaining:99999})` → должен быть `permission-denied`. Добавить это как автотест через `@firebase/rules-unit-testing` (эмулятор).

### 1.2 Право ключа биржи (`read_only`/`trade`) приходит из запроса [КОД]
- Где: `server.ts` маршрут `POST /api/exchanges/order` читает `permissions` из `req.body`.
- Риск: проверка «ключ только для чтения» обходится подменой поля. Реальную защиту даёт лишь то, какие права выданы самому ключу на бирже.
- Исправить: хранить `permissions` на сервере (в документе, который клиент не может менять), читать оттуда по `exchangeId`; клиенту не доверять ни `permissions`, ни шифртексты ключей.

### 1.3 Шифрование ключей бирж: публичный запасной ключ и общий мастер-ключ [КОД]
- Где: `server/security.ts` — `getVaultKey`: `process.env.TOTP_MASTER_KEY || process.env.GEMINI_API_KEY || 'aegisquant-institutional-vault-2026'`; ключ = `sha256(master:uid:totp-v1)`.
- Риски:
  1. Без переменных окружения шифрование использует константу из публичного репозитория.
  2. Один и тот же мастер-ключ защищает TOTP-секреты и API-ключи бирж; при подмене на `GEMINI_API_KEY` смена/утечка Gemini-ключа ломает или раскрывает данные.
  3. Обычный SHA-256 без соли и без версии ключа: нет ротации.
- Исправить: при отсутствии `TOTP_MASTER_KEY` сервер **не стартует** (в production); убрать fallback на `GEMINI_API_KEY` и на константу; отдельные ключи для TOTP и для бирж; HKDF вместо голого SHA-256; поле `keyVersion` в шифртексте для ротации.
- Проверить: `NODE_ENV=production` без `TOTP_MASTER_KEY` → процесс завершается с ошибкой. [ПРОВЕРИТЬ] режим шифрования в `encryptSecret` (должен быть AES-256-GCM, случайный IV 12 байт на каждое шифрование, проверка auth-tag); я эту функцию целиком не читал.

### 1.4 Ключи бирж проходят через клиента [КОД]
- Где: `/api/exchanges/connect` возвращает `encryptedApiKey/Secret/Passphrase` клиенту; клиент пишет их в Firestore (`exchangeKeys` в rules), потом присылает обратно в `/sync` и `/order`.
- Риски: клиент контролирует, какой шифртекст подставить; ключи лежат в базе, доступной клиенту по чтению; при утечке мастер-ключа утекают все.
- Исправить: сервер сам записывает ключи в закрытую коллекцию (клиентам `allow read, write: if false`), клиенту отдаётся только `exchangeId`, `label`, маска ключа и права; `/sync` и `/order` принимают только `exchangeId`.

### 1.5 Торговые ордера без серверных ограничений [КОД: не найдено]
- В `server/exchanges.ts` я не нашёл: максимум размера ордера, дневной лимит, список разрешённых пар, ключа идемпотентности, повторной проверки 2FA, журнала аудита. Окно подтверждения есть только в интерфейсе (`TradeRiskConfirmModal`).
- Исправить: до полной проверки оставить режим «только чтение» и testnet; для `trade`: серверный лимит на ордер/день, обязательный 2FA (TOTP) на каждый ордер или сессию, `clientOrderId`/идемпотентность, запись в `users/{uid}/auditLog` (только сервер), kill-switch переменной окружения `TRADING_ENABLED=false`.
- Рекомендация по правам: инструкция пользователю — создавать ключ без права вывода средств и с привязкой к IP сервера (если биржа позволяет).

### 1.6 PIN-блокировка — не защита данных [КОД]
- Где: `src/lib/securityDlp.ts` `hashPinSha256`, `src/App.tsx` (`getPinHash`/`setPinHash`), `PinLockOverlay.tsx` сравнивает хеш на клиенте.
- Риски: SHA-256 от короткого PIN подбирается мгновенно (4–6 цифр = 10⁴–10⁶ вариантов); проверка в браузере обходится через DevTools; PIN не шифрует данные.
- Исправить: не называть это защитой данных (только «экранная блокировка»); если нужно настоящее — PBKDF2/Argon2 с солью + ключ шифрования локальных данных, лимит попыток с задержкой, либо WebAuthn.
- [ПРОВЕРИТЬ] где хранится `pinHash` (localStorage/Firestore) — если в Firestore, то правила не должны позволять читать его чужим.

### 1.7 Публичные скриншоты в репозитории [КОД]
- Где: `public/assets/aistudio/*` (5 PNG + README). Раздаются сайтом, в коде не используются, видны оператор связи и фрагменты интерфейса.
- Исправить: удалить файлы и папку; просмотреть историю git на другие случайно закоммиченные файлы.

### 1.8 Ключи NOWPayments были показаны в чате [КОД/история]
- API-ключ и IPN-секрет присылались в переписке. Считать скомпрометированными.
- Исправить: перегенерировать IPN-секрет (можно в кабинете), попросить поддержку заменить API-ключ, прописать новые только в Secrets AI Studio; проверить, что в репозитории и истории git их нет (п. 6.2).

## 3. Аутентификация и 2FA

- 3.1 [КОД] Токен Firebase проверяется через `jose` на сервере (`requireAuth`). [ПРОВЕРИТЬ]: проверяются `aud` (= project id), `iss` (`https://securetoken.google.com/<project>`), срок, `sub` непустой; ключи берутся из официального JWKS и кэшируются; **`auth_time` и отзыв токена** (`checkRevoked`) для чувствительных операций (платёж, ордер, смена 2FA).
- 3.2 [КОД] TOTP: секрет шифруется на сервере. [ПРОВЕРИТЬ]: окно допуска кода ≤ ±1 шаг; код нельзя использовать повторно (хранить последний принятый шаг); сравнение за постоянное время (`crypto.timingSafeEqual`); лимит попыток на аккаунт (п. 2.6); резервные коды хранить хешами.
- 3.3 [ПРАКТИКА] В консоли Firebase Auth: включить защиту от перебора e-mail (email enumeration protection), оставить только нужные провайдеры, проверить список Authorized domains (убрать лишние), политика паролей, MFA для администраторов проекта.
- 3.4 [КОД] В клиенте есть собственный `SESSION_STORAGE_KEY` (useAuthAndVault). [ПРОВЕРИТЬ] что сервер не доверяет этому значению как доказательству сессии.
- 3.5 [ПРАКТИКА] Выход со всех устройств/отзыв токенов (`revokeRefreshTokens`) при смене 2FA и при подозрительной активности.

## 7. Платежи (NOWPayments)

В main серверную часть биллинга я не дочитал [ПРОВЕРИТЬ]. На моей ветке реализовано, перенос в main нужно сверить:
- [ ] Подпись IPN: HMAC-SHA512 от JSON с отсортированными ключами, сравнение через `crypto.timingSafeEqual`; без подписи/с неверной подписью → 401, ничего не меняется.
- [ ] Идемпотентность: повторный IPN с тем же `payment_id` не продлевает подписку дважды (хранить обработанные id).
- [ ] План и срок определяются **на сервере** по `order_id`, созданному серверной стороной; сумма и валюта сверяются с ожидаемыми; статусы `partially_paid`, `expired`, `failed` не активируют PRO/MAX.
- [ ] `order_id` не угадывается и привязан к `uid`; пользователь не может активировать чужой заказ.
- [ ] Активация плана пишется только через firebase-admin; клиент не может писать `plan/proUntil` (п. 1.1).
- [ ] Для MAX: проверить, что цена, квоты (25/100/…), `maxMultiplier` и срок задаются таблицей на сервере, а не приходят из клиента.
- [ ] Новые ключи (п. 1.8) заданы только в Secrets; IPN-адрес — только HTTPS-домен приложения.
- [ ] Страница-возврат после оплаты не выдаёт доступ; доступ даёт только подтверждённый IPN.
