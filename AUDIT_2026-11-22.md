## 2. Новые и оставшиеся проблемы

### P0

**1. Захват 2FA при краже сессии (повторная регистрация без проверки)** [ПРОВЕРЕНО]
`/api/security/totp/setup` и `/api/security/totp/confirm` не проверяют, что у пользователя уже включён 2FA и что он подтвердил его только что. Тот, кто получил чужую сессию (ровно тот сценарий, от которого защищает 2FA), делает: `setup` → сканирует свой QR → `confirm` с кодом из своего приложения. Сервер **перезаписывает** секрет и резервные коды в `serverSecurity/totp`, выдаёт новые резервные коды и `stepUpUntil` на 10 минут. После этого ордера на testnet и любые будущие защищённые операции проходят.
Исправить: если серверная запись 2FA уже существует — `setup/confirm` требуют действующий `stepUpUntil` или текущий TOTP/резервный код; добавить серверный маршрут «отключить 2FA» (код + step-up); при смене 2FA отправлять push-уведомление «2FA изменён» и вносить событие в журнал. Тест: сессия без step-up не может перезаписать секрет.

**2. Шаг-ап 2FA обходится или не применяется** [ПРОВЕРЕНО]
- Проверяется **только** в `/api/exchanges/order` и только если в `serverSecurity/totp` уже есть секрет. На `/api/exchanges/connect` и `/api/exchanges/sync` (чтение баланса, привязка ключей) проверки нет.
- Пользователи, включившие 2FA до обновления (секрет лежит в клиентской записи `users/{uid}/private/security`), серверной записи не имеют: ордер для них проходит без шаг-апа. Для таких `/verify` ещё и подставляет `encryptedSecret` из тела запроса, если серверной записи нет; в `private/security` клиент может писать (правила Firestore).
- Если нет Admin SDK, проверка шаг-апа просто пропускается (не отказ).
- Нет серверного «отключить 2FA»: клиентский флаг `twoFactorEnabled` в правилах по-прежнему меняется самим клиентом, но серверный секрет остаётся.
Исправить: единая функция `requireStepUp(uid)` — отказ, если нет Admin SDK; применять к `connect`, `sync`, `order`, удалению ключей и смене 2FA; для старых пользователей: считать 2FA включённым по `private/security`/`twoFactorEnabled` и требовать повторную настройку (миграция в серверную запись); убрать из `/verify` использование `encryptedSecret` и `backupCodeHashes` из тела запроса в production; убрать чтение клиентской `private/security` как источника секрета.

**3. Приложение в превью работает в «разработческом» режиме** [ПРОВЕРЕНО по коду, значения окружения НЕ ПРОВЕРЕНЫ]
Много защит включается только при `NODE_ENV=production`: CSP, отказ от запуска без `TOTP_MASTER_KEY`, 503 без Admin SDK, запрет клиентских хешей резервных кодов, отказ при неподключённой базе поддержки. Без `NODE_ENV=production` в превью AI Studio и на любом хостинге без этой переменной действуют мягкие правила (память вместо базы, эфемерный ключ шифрования).
Исправить/проверить: на боевом хостинге `NODE_ENV=production`; добавить в `/api/health` поле `securityMode` («production-strict» или «dev»), чтобы владелец видел режим; тест на запуск без переменной.

### P1

**4. Покупка другого тарифа сжигает оплаченные дни** [ПРОВЕРЕНО]
В `processIpn`: `base = isSamePlan ? max(now, currentUntil) : now`. Человек с годовым PRO покупает MAX на месяц — оставшиеся месяцы PRO пропадают без возврата. Исправить: пересчёт остатка (в пересчёте на стоимость) или запрет покупки другого тарифа до окончания текущего, либо очередь «следующий период»; явное предупреждение на экране оплаты; тест.

**5. Суточный бюджет Gemini — общий и в памяти** [ПРОВЕРЕНО]
`consumeGeminiDailyBudgetOrThrow` ведёт один счётчик на весь сервер (500/день). Один вошедший пользователь (или бот с Google-аккаунтами) за минуты исчерпывает его — ИИ-функции недоступны всем. Счётчик сбрасывается при перезапуске. Исправить: отдельные лимиты на пользователя и общий; хранение в Firestore (атомарный счётчик по дате); оповещение владельцу при 80%; кэш ответов для одинаковых запросов.

**6. Анонимные затратные маршруты остались** [ПРОВЕРЕНО]
`/api/strategies/pnl|scanner|sentiment`, `/api/market/*`, `/api/widgets/feed`, `/api/news`, `/api/economic-calendar` доступны без входа (12 запросов в минуту на IP для «тяжёлых»). Это нагрузка на биржевые API и вычисления, плюс анонимные пользователи получают бесплатный доступ ко всем возможностям Free. Решите продуктово: оставить как «демо» с жёстким кэшем и общим бюджетом или требовать вход для сканера и PnL.

**7. Анонимная запись в базу через `/api/support`** [ПРОВЕРЕНО]
Любой может создавать документы в `supportInbox` (до 12 в минуту с одного IP; `contactEmail` проверяется только на «содержит @»). Исправить: App Check/капча, суточный лимит на IP и на e-mail, проверка формата e-mail, TTL документов, уведомление владельцу.

**8. Состояние всё ещё частично в памяти** [ПРОВЕРЕНО]
`stepUpUntilByUid`, `lastTotpStepByUid`, `serverBackupHashesByUid`, `authFailureTracker`, реестр `serverVerifiedKeyRegistry`, реестры push, хранилище `express-rate-limit`. Размеры теперь ограничены (хорошо), но после перезапуска или на нескольких экземплярах Cloud Run блокировки, push-подписки и ценовые алерты теряются. Решение: Firestore (серверные записи с TTL) или Redis; пока — один экземпляр и честная запись об этом в README.

**9. App Check не подключён** [ПРОВЕРЕНО]
В CSP добавлены хосты reCAPTCHA и App Check, но `initializeAppCheck` в `src/` нет. Либо подключить (раздел 3, E2), либо убрать лишние разрешения из CSP.

**10. Нет проверки отзыва токена; сервер принимает токены до часа после смены доступа** [ПРОВЕРЕНО]
`requireAuth` проверяет подпись, `iss`, `aud` и срок, но не `checkRevoked`. Для ордеров, 2FA, ключей и оплаты нужна проверка отзыва и свежести входа (`auth_time`).

**11. Зависимости** [ПРОВЕРЕНО: `bun audit`]

**12. Тесты не покрывают самое важное** [ПРОВЕРЕНО]
19 тестов проверяют чистую логику (кредиты, шифрование, TOTP-шаги, подпись IPN, PDF, логи биржи). (2) Добавь автотест или приложи вывод команды, доказывающий исправление; для маршрутов Express — HTTP-тест с подставной авторизацией. (7) После каждой группы запускай `bun run lint`, `bun run build`, `bun run test`, `bun audit` и показывай результат. (8) Не пиши секреты и реальные ключи в код, тесты и комментарии. (9) Коммить небольшими коммитами, один смысл — один коммит.
>
> **Группа G — 2FA и защита операций (P0)**
> G1. Захват 2FA: в `/api/security/totp/setup` и `/confirm`, если серверная запись `users/{uid}/serverSecurity/totp` уже существует с секретом, требуй действующий `stepUpUntil` (не истёк) **или** валидный текущий TOTP/резервный код в теле запроса. Иначе — 403 `STEP_UP_REQUIRED`. Добавь серверный маршрут `POST /api/security/totp/disable` (код + step-up). При любой смене 2FA отправляй push `security-event` и пиши запись в `users/{uid}/securityLog` (только Admin SDK).
